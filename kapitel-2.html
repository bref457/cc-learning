Richtig arbeiten: bessere Ergebnisse mit weniger Korrekturen

Wie du Aufgaben so stellst, dass Claude beim ersten Mal das Richtige baut, wie du den bewährten Ablauf aus Erkunden, Planen, Umsetzen und Prüfen nutzt und wie du eine Sitzung im Griff behältst.

⏱️ ca. 40 Minuten 🎯 Einsteiger bis Fortgeschrittene ❓ 12 Quizfragen 🃏 16 Merkkarten
1

Warum es manchmal hakt

Claude Code ist so gebaut, dass schon ein einfacher erster Prompt meistens das Richtige tut. Wenn nicht, steckt fast immer einer von vier Gründen dahinter.

Ohne dass du etwas einrichtest, erledigt Claude Code schon vieles von selbst: Neue Sitzungen im Terminal und in VS Code starten im Auto-Modus, sodass du nicht jeden Befehl absegnen musst. Unabhängige Teilarbeit gibt Claude an Helfer (Subagenten) ab. Und lange Gespräche werden automatisch zusammengefasst, bevor das Kontextfenster voll ist.

Schwierig wird es dort, wo dein Projekt Wissen, Regeln oder Grenzen hat, die nicht im Code stehen. Kein Standard kann das erraten.

🙈

Es fehlt Wissen

Claude baut etwas anderes als gedacht oder muss in jeder Sitzung dieselbe Sache neu herausfinden.

Lösung: sag, was es nicht sehen kann
🤷

„Fertig“, aber nicht ganz

Claude meldet Erfolg, doch es funktioniert nicht. Meist hatte es keine Möglichkeit, sich selbst zu prüfen.

Lösung: gib ihm eine Prüfung
🚫

Eine Regel wurde gebrochen

Claude tut etwas, das nie passieren darf, oder lässt einen Pflichtschritt aus.

Lösung: Regeln fest durchsetzen
💸

Zu teuer erkauft

Das Ergebnis stimmt, aber es hat mehr Zeit, Token oder Rückfragen gekostet als nötig.

Lösung: eine Voreinstellung ändern
📌 Merke

Bevor du an Einstellungen schraubst, frag dich: Fehlte Claude Wissen, eine Prüfung, eine feste Regel oder passte eine Voreinstellung nicht? Dieses Kapitel geht alle vier durch.

2

Gute Prompts schreiben

Ein guter Prompt gibt Claude genau das, was es nicht selbst im Code findet. Mehr nicht.

Claude beginnt jede Aufgabe damit, deinen Code zu lesen, und darin ist es sehr gut. Dateistruktur, Konventionen, Test-Framework: das findet es meist schneller, als du es erklären könntest. Was es nicht finden kann, ist alles, was nie im Repo stand: eine Entscheidung aus einem Meeting, ein Ablauf, den nur eine Person im Kopf hat, oder welche von zwei guten Lösungen du bevorzugst.

Die Faustregel: Ort, Symptom, Ziel

Nenne wo du suchen würdest, was genau passiert und woran man erkennt, dass es gelöst ist. Das spart fast immer eine Korrekturrunde.

❌ Vage„Behebe den Login-Bug.“
✅ Spezifisch„Nutzer melden, dass der Login nach einem Sitzungs-Timeout fehlschlägt. Schau dir den Token-Refresh in src/auth/ an, schreib einen Test, der den Fehler nachstellt, und behebe ihn dann.“
❌ Vage„Füg ein Kalender-Widget hinzu.“
✅ Spezifisch„Bau nach dem Muster von HotDogWidget.php ein Kalender-Widget, mit dem man einen Monat wählen und zwischen Jahren blättern kann. Keine neuen Bibliotheken.“

Material direkt mitgeben statt beschreiben

📄

Datei mit @

Tippe @ und den Pfad, z. B. @src/utils/auth.js. Der Inhalt landet direkt in deiner Nachricht. Mit @ordner/ geht es auch für Verzeichnisse.

🖼️

Bild

Screenshot eines Fehlers oder Designs per Drag & Drop, oder einfügen mit Ctrl+V (unter Windows Alt+V).

📜

Befehlsausgabe

Aus der Shell hineinleiten: cat error.log | claude -p "Was ist hier los?"

„Denk Schritt für Schritt“ ist kein Zauberwort

Sätze wie „denk gründlich nach“ oder „think step by step“ sind ganz normaler Text. Sie stupsen Claude höchstens leicht an. Wie viel Claude wirklich nachdenkt, steuerst du mit der Effort-Stufe (siehe Abschnitt 10). Die einzige Ausnahme ist das Schlüsselwort ultrathink.

💡 Tipp: „Sei ambitioniert“

Claude liest eine Anfrage eher zurückhaltend und baut das Kleinste, was sie erfüllt. Es kann ja nicht sehen, wie viel du dir erhoffst. Willst du die umfassende Version, sag es:

Prompt
Bau die Einstellungsseite nach dem Mockup. Sei ambitioniert:
leere Zustände und Fehlerzustände, Speichern funktioniert,
Tastaturbedienung, nicht nur das Layout.

Damit sagst du Claude, welchen Umfang du willst, nicht wie intensiv es denken soll.

ℹ️ Vage ist manchmal genau richtig

Wenn du nur erkunden willst, passt ein offener Prompt wie „Was würdest du an dieser Datei verbessern?“ völlig. Du korrigierst unterwegs etwas mehr, dafür entdeckst du Dinge, an die du nicht gedacht hättest.

3

Unklar, was du willst? Lass dich interviewen

Du musst nicht alles fertig durchdacht haben, bevor du anfängst. Dreh den Spieß um und lass Claude die Fragen stellen.

Prompt
Ich will für die öffentliche API ein Rate-Limit einbauen, habe es mir
aber noch nicht genau überlegt. Interview mich, bis du daraus eine
Spezifikation schreiben kannst, und speichere sie dann in SPEC.md.
  1. Claude fragt nach Es stellt dir Multiple-Choice-Fragen zu allem, was noch offen ist: Limit pro Nutzer oder pro Schlüssel? Was passiert mit Anfragen über dem Limit? Was gehört ausdrücklich nicht dazu?
  2. Die Spezifikation entsteht Aus deinen Antworten schreibt Claude SPEC.md: eine schriftliche Definition von „fertig“.
  3. Frisch starten und bauen Starte für die Umsetzung eine neue Sitzung (oder /clear). So beginnt die Arbeit mit sauberem Kontext und klarem Ziel.
  4. Später dagegen prüfen Dieselbe Datei nutzt du am Ende, um das Ergebnis prüfen zu lassen (siehe Abschnitt 7).
🧭 Beispiel außerhalb von Code

Das klappt auch für Nicht-Programmier-Aufgaben: „Ich will meine Fotosammlung neu ordnen. Interview mich zu meinen Wünschen und schreib dann einen Plan in PLAN.md.“

4

Der bewährte Ablauf: erkunden, planen, umsetzen, prüfen

Bei größeren Aufgaben lohnt es sich, nicht gleich „Bau mal“ zu sagen, sondern in vier Etappen zu arbeiten.

💡 Nicht für jede Aufgabe

Planen kostet Zeit. Für eine kleine, klare Änderung (Tippfehler, Umbenennung, eine Zeile Log) sag einfach direkt, was du willst. Den vollen Ablauf brauchst du, wenn du dir beim Weg unsicher bist, mehrere Dateien betroffen sind oder du den Code nicht gut kennst.

5

Der Plan-Modus im Detail

Im Plan-Modus darf Claude lesen, suchen und erkunden, aber keine Dateien ändern, bis du den Plan freigibst.

So kommst du hinein

Drück Shift+Tab, bis unten ⏸ plan mode on steht. Nochmal Shift+Tab verlässt den Modus wieder.

Stell dem Prompt /plan voran:

Prompt
/plan Wie würdest du die Benutzerverwaltung auf die neue Datenbank umziehen?
Terminal
claude --permission-mode plan

Wer immer mit einem Plan starten will, kann den Plan-Modus pro Projekt als Standard festlegen. Das zeigen wir in Kapitel 4.

Den Plan prüfen und freigeben

Ist der Plan fertig, zeigt Claude ihn und fragt, wie es weitergehen soll:

AuswahlWas dann passiert
Yes, and use auto modePlan genehmigt, Claude setzt ihn im Auto-Modus um, ohne bei Alltäglichem zu fragen.
Yes, manually approve editsPlan genehmigt, du bestätigst aber jede einzelne Änderung.
No, keep planningDu bleibst im Plan-Modus und sagst Claude, was am Plan anders werden soll.
💡 Plan selbst bearbeiten

Drück Ctrl+G, um den Plan in deinem Texteditor zu öffnen. Streich Schritte, ergänze Hinweise, speichere, und Claude arbeitet mit deiner Fassung weiter.

⚠️ Achtung bei Shift+Tab

Wenn die Genehmigungsabfrage offen ist, genehmigt Shift+Tab den Plan. Willst du nur raus, drück zuerst Esc.

Typische Abläufe als Prompt-Rezepte

Für die häufigsten Aufgaben gibt es bewährte Formulierungen. Nimm sie als Startpunkt und pass sie an.

Erst den Überblick, dann immer genauer werden.

Prompts
Gib mir einen Überblick über dieses Projekt.
Erklär mir die wichtigsten Muster in der Architektur.
Wo wird die Benutzer-Anmeldung behandelt?
Verfolge den Ablauf beim Login vom Frontend bis zur Datenbank.

Tipp: Frag nach Begriffen aus deinem Fachgebiet. Claude findet die passenden Stellen.

Gib die Fehlermeldung und, wenn möglich, wie man den Fehler auslöst.

Prompts
Beim Ausführen von npm test kommt ein Fehler. Hier ist er: [Fehler einfügen]
Schlag mir ein paar Wege vor, den Fehler zu beheben.
Behebe ihn mit dem Ansatz, der die Ursache angeht, nicht nur das Symptom.

Sag Claude, ob der Fehler immer oder nur manchmal auftritt, und wie man ihn nachstellt.

Erst finden, dann Vorschläge, dann in kleinen, geprüften Schritten umbauen.

Prompts
Finde veraltete API-Aufrufe in unserem Projekt.
Schlag vor, wie wir utils.js modernisieren können.
Bau es um, aber das Verhalten muss gleich bleiben.
Lass danach die Tests für den umgebauten Code laufen.

Claude schaut sich deine bestehenden Tests an und übernimmt Stil und Framework.

Prompts
Finde Funktionen in NotificationsService.swift, die nicht getestet sind.
Schreib Tests dafür.
Ergänze Grenzfälle: leere Eingaben, sehr große Werte, Netzwerkfehler.
Lass die neuen Tests laufen und behebe, was fehlschlägt.
Prompts
Fasse meine Änderungen zusammen.
Erstell einen Pull Request.
Ergänze die Beschreibung um den Sicherheitsaspekt.

Braucht git und am besten die GitHub-CLI gh, angemeldet. Dann öffnet Claude den PR direkt.

Prompts
Finde Funktionen ohne passende Kommentare im Ordner auth.
Ergänze Kommentare im Stil des Projekts.
Prüf, ob die README noch zum aktuellen Stand passt.
💡 Frag Claude nach Claude

Unsicher, wie man etwas am besten angeht? Frag einfach: „Wie würdest du hier vorgehen?“ oder „Was kannst du mit Bildern machen?“. Claude kennt seine eigene Dokumentation.

7

Gib Claude eine Prüfung mit

Claude hört auf, wenn die Arbeit fertig aussieht. Kann es nicht nachprüfen, ob sie fertig ist, wirst du selbst zur Testabteilung.

Gib Claude etwas, das mit bestanden oder fehlgeschlagen antwortet. Dann schließt Claude die Schleife selbst: ändern, prüfen, Fehler lesen, verbessern, erneut prüfen. Und du musst nicht danebensitzen.

🧪

Tests

Eine Testdatei oder die ganze Test-Suite.

🏗️

Build & Typecheck

Der Exit-Code sagt eindeutig: geht oder geht nicht.

🧹

Linter

Stil- und Fehlerprüfung auf Knopfdruck.

🔁

Vergleichsskript

Ausgabe gegen eine erwartete Datei prüfen.

📸

Screenshot

Bei Oberflächen: Screenshot neben dem Mockup.

📋

Spezifikation

Eine SPEC.md, gegen die geprüft wird.

Wie streng soll die Prüfung sein?

VarianteWann sinnvoll
Im PromptFunktioniert sofort für jede Aufgabe, ohne Einrichtung. Claude entscheidet selbst, wann es zufrieden ist.
/goalZ. B. /goal alle Tests in tests/auth sind grün und der Linter meldet nichts. Wichtig bei langen Läufen, bei denen Claude sonst mit einem Zwischenstand aufhören könnte.
/code-reviewEin neuer Subagent prüft deine Änderungen. Er hat das Gespräch nie gesehen und lässt sich nicht von der Begründung beeinflussen, die zum Code geführt hat.
Stop-HookEin Skript, das bei jedem Versuch aufzuhören läuft und Claude zurückschickt, solange es fehlschlägt. Wie man Hooks baut, kommt in Kapitel 5.
📌 Merke: Belege verlangen

„Alle Tests bestanden“ sagt wenig. Bitte Claude um den ausgeführten Befehl und seine Ausgabe oder um den Screenshot. Die Ausgabe zu lesen geht schneller, als selbst noch einmal zu prüfen. Und bei einer Sitzung, die du nicht beobachtet hast, ist das dein einziger Beweis.

Gegen deine Spezifikation prüfen lassen

Prompt
Lass einen Subagenten den Rate-Limiter-Diff gegen SPEC.md prüfen:
Ist jede Anforderung umgesetzt, haben die genannten Grenzfälle Tests?
Melde nur Lücken, die die Korrektheit betreffen, und lass Stilfragen weg.
⚠️ „Stil weglassen“ nicht vergessen

Ein Prüfer, der Probleme finden soll, findet immer etwas. Wer jeden Befund umsetzt, landet bei unnötigen Abstraktionen und Tests für Fälle, die nie eintreten.

💡 /verify

Wenn Claude fertig ist, startet /verify die App, schaut sich das Ergebnis an und findet so Probleme, die Tests und Typecheck übersehen.

8

Bitte oder Regel? Zwei Arten von Anweisungen

Manches darfst du Claude überlassen, manches muss jedes Mal so passieren. Dafür gibt es zwei verschiedene Werkzeuge.

🧠

Bitte (Claude entscheidet)

Dein Prompt, die CLAUDE.md, ein Skill. Claude liest es und folgt dem fast immer, aber es gibt keine Garantie. Es darf entscheiden, dass eine Richtlinie hier nicht passt.

für Richtlinien mit Ausnahmen
⚙️

Regel (Claude Code setzt durch)

Ein Hook, eine Verbotsregel (deny), eine verwaltete Einstellung. Claude Code wendet sie jedes Mal an, egal was das Modell denkt.

für „immer“ und „nie“
Claude entscheidetClaude Code setzt durch
Was zu tun istPrompt, CLAUDE.md, SkillsHooks, Skills, die nur du startest
Worauf es zugreiftder Prüfer im Auto-Modusdeny-Regeln, Sandbox
Wann es fertig istBitte um Belege, /goal, /code-reviewTests, Stop-Hook, CI
Wie viel es ausgibtEffort-StufeTurn- oder Budget-Limit
🧭 Beispiel

„Bevorzuge benannte Exporte“ ist eine Vorliebe mit vielen Ausnahmen: gehört in die CLAUDE.md. „Lies niemals .env“ darf keine Ausnahme haben: gehört in eine deny-Regel. „Nach jeder Änderung Formatierer laufen lassen“: gehört in einen Hook.

💡 Das Warnsignal

Wenn du eine Zeile in der CLAUDE.md immer lauter formulierst („WICHTIG!“, „IMMER!“) und Claude sie trotzdem übersieht, gehört sie in einen Hook. Und umgekehrt: Hooks für reine Vorlieben kannst du löschen und Claude entscheiden lassen.

Die CLAUDE.md lernst du in Kapitel 3 kennen, Berechtigungsregeln und Sandbox in Kapitel 4, Hooks und Skills in Kapitel 5.

9

Die Sitzung steuern

Keine Einstellung ersetzt es, die erste Minute zuzuschauen und einzugreifen, sobald Claude in die falsche Richtung läuft.

Die drei wichtigsten Griffe

✋

Esc

Stoppt Claude mitten in der Arbeit. Alles bis dahin bleibt erhalten, du kannst direkt umlenken.

⏪

/rewind oder Esc Esc

Spult Code, Gespräch oder beides zu einem früheren Prompt zurück. Alias: /undo.

🧽

/clear

Frischer Start ohne den bisherigen Verlauf. Das alte Gespräch bleibt über /resume erreichbar.

Die Zwei-Korrekturen-Regel

Wenn du dasselbe zweimal korrigiert hast und es immer noch nicht stimmt, fügt eine dritte Korrektur vor allem weiteren Ballast hinzu. Ein frischer Start mit einem Prompt, der das Gelernte gleich einbaut, klappt fast immer besser.

Das Rewind-Menü

OptionWas sie tut
Restore code and conversationCode und Gespräch zurück auf diesen Punkt
Restore conversationNur das Gespräch zurück, der Code bleibt wie er ist
Restore codeNur die Dateiänderungen zurück, das Gespräch bleibt
Summarize from hereAlles ab hier zu einer Zusammenfassung verdichten, schafft Platz
Summarize up to hereAlles vor diesem Punkt verdichten, Späteres bleibt unverändert
💡 Mutig ausprobieren

Weil Zurückspulen so einfach ist, kannst du zuerst den mutigeren Ansatz probieren lassen. Klappt er nicht, spulst du zurück und nimmst den sicheren Weg.

⚠️ Checkpoints ersetzen kein Git

Zurückgespult werden nur Dateien, die Claude mit seinen eigenen Bearbeitungs-Tools geändert hat. Was nur ein Shell-Befehl verändert hat, was ein Hintergrund-Subagent geändert hat oder was du selbst nebenher bearbeitet hast, bleibt wie es ist. Nutze deshalb immer auch git.

Kleine Helfer

BefehlWofür
/btwEine kurze Zwischenfrage stellen, ohne dass sie im Verlauf landet
/rename nameDer Sitzung einen Namen geben, z. B. /rename oauth-umbau
claude --resume nameEine benannte Sitzung später wieder aufnehmen, samt Checkpoints
claude --continueDie letzte Sitzung im Ordner fortsetzen
Tippen während Claude arbeitetDeine Nachricht wird eingereiht und nach dem aktuellen Schritt gelesen

10

Effort und Modell: wie viel Denken soll es sein?

Die Effort-Stufe ist der wichtigste Regler dafür, wie gründlich Claude nachdenkt. Sie ersetzt fast alles, was man früher mit Zauberformeln im Prompt versucht hat.

StufeWann sinnvoll
lowSchnelles Hin und Her, bei dem du jedes Ergebnis ohnehin anschaust: Brainstorming, erster Entwurf, Umbenennung über ein paar Dateien.
mediumStandard. Passt für alltägliche Arbeit mit klarem Umfang, z. B. eine neue Funktion bauen.
high / xhighWenn es auf leicht übersehene Fälle ankommt: Fehler in fremdem Code, wackelige Tests, eine Schemaänderung, bei der jede Stelle gefunden werden muss.
maxSchwere Probleme, die Claude ohne dich durcharbeiten soll, etwa die Suche nach einer Sicherheitslücke. Bei normalen Aufgaben denkt es dann eher zu viel und kostet mehr, ohne besser zu sein.

So stellst du es ein

WegWirkung
/effortÖffnet einen Schieberegler. Enter speichert als Standard, s gilt nur für diese Sitzung.
/effort highStellt die Stufe direkt ein.
claude --effort lowStufe für eine einzelne Sitzung beim Start.
ultrathink im PromptNur für diese eine Nachricht tiefer nachdenken, ohne die Einstellung zu ändern. Im Terminal erscheint das Wort in Regenbogenfarben.

Und welches Modell?

🎼

Opus

Standardmodell auf den meisten Plänen. Erledigt die meisten Programmieraufgaben sehr gut.

🎵

Sonnet

Günstiger für alltägliche Arbeit.

🍃

Haiku

Klein und schnell. Gut für Helfer (Subagenten) mit einfachen Aufgaben.

Wechseln mit /model. Dort kannst du mit den Pfeiltasten links/rechts auch gleich den Effort anpassen.

Den passenden Berechtigungsmodus wählen

Die Modi kennst du aus Kapitel 1. Hier geht es darum, welcher für deine Arbeitsweise passt.

✋

Manual

Du genehmigst jede Änderung selbst. Sicher, aber nach der zehnten Frage klickst du ohne zu lesen, und ohne dich geht nichts weiter.

gut zum Lernen
🤖

Auto

Standard. Claude arbeitet durch, ein separater Prüfer stoppt Riskantes: z. B. curl | bash, Produktions-Deployments, Force-Push über fremde Arbeit, sensible Daten nach außen.

der gute Mittelweg
⚡

bypassPermissions

Genehmigt alles, was keine Verbotsregel abdeckt. Nur in einem Wegwerf-Container sinnvoll.

mit Vorsicht
ℹ️ Wenn der Auto-Modus blockiert

Du bekommst einen Hinweis, und die Aktion steht unter Recently blocked in /permissions. Dort kannst du sie freigeben. Nach drei Blockaden hintereinander (oder zwanzig insgesamt) pausiert der Auto-Modus und fragt wieder dich.

⚠️ Gesagt ist nicht gesichert

„Pushe nicht, bevor ich es geprüft habe“ im Gespräch nimmt der Prüfer ernst. Aber der Satz kann beim Zusammenfassen des Gesprächs verloren gehen. Was wirklich wichtig ist, gehört in eine feste Regel (Kapitel 4).

💡 Zu viele Rückfragen?

/fewer-permission-prompts durchsucht deine letzten Sitzungen nach häufigen, nur lesenden Befehlen und schlägt vor, sie dauerhaft zu erlauben.

12

Kosten und Kontext im Blick behalten

Jede Anfrage schickt das ganze bisherige Gespräch mit. Eine Sitzung, die drei fremde Aufgaben angesammelt hat, bezahlt bei der vierten alle drei mit.

📊

/usage

Erste Anlaufstelle. Zeigt, wohin dein Verbrauch geht, aufgeschlüsselt nach Skills, Subagenten, Plugins und MCP-Servern, und warnt vor teuren Mustern.

🧽

/clear zwischen Aufgaben

Kostet nichts und die nächste Aufgabe zahlt nicht für den alten Verlauf. /clear oauth-umbau benennt dabei die alte Sitzung.

🗜️

/compact mit Fokus

Z. B. /compact behalte die API-Änderungen und die Testbefehle. Achtung: Das Zusammenfassen liest selbst das ganze Gespräch und ist eine große Anfrage.

👥

Subagenten kosten mit

Jeder Helfer schickt eigene Anfragen, die zu deiner Nutzung zählen. Er bringt Parallelität und frischen Blick, aber keine klügere Antwort.

ℹ️ Der Cache

Bereits gesendete Teile des Gesprächs werden zwischengespeichert und sind dann günstiger. Bei einem Abo hält dieser Cache etwa eine Stunde. Nach einer längeren Pause ist eine neue Sitzung daher oft günstiger als weiterzumachen.

Kontextfenster, CLAUDE.md und das Gedächtnis vertiefen wir in Kapitel 3, Subagenten in Kapitel 6.

📖 Original: Kosten und Kontext gering halten ↗
13

Claude allein arbeiten lassen

Solange du zuschaust, fängst du Fehler nach ein, zwei Nachrichten ab. Bei einem Lauf über Nacht sagt es Claude niemand.

Bevor du eine Aufgabe unbeaufsichtigt laufen lässt, geh diese fünf Fragen durch:

  1. Weiß es, wie „fertig“ aussieht?Ein Ziel, eine Spezifikationsdatei oder ein roter Test, der grün werden muss.
  2. Kann es seine Arbeit selbst prüfen?Test-Suite, Stop-Hook oder ein Review-Schritt.
  3. Was darf es anfassen?Berechtigungsregeln, Sandbox, ein eigener Worktree, nur ein bestimmter Branch.
  4. Was stoppt es?Ein Limit für Durchgänge (--max-turns) oder Kosten (--max-budget-usd).
  5. Wer gibt das Ergebnis frei?Ein Pull Request oder eine Zusammenfassung, und dann ein Mensch, der Merge oder Deployment genehmigt.
💡 Klein anfangen

Lass einen neuen Ablauf zuerst mit drei Dateien laufen, schau, was schiefgeht, verbessere den Prompt, und erst dann den Rest. Und beobachte die ersten Läufe von allem Neuen, bevor du ihm blind vertraust.

Skripte mit claude -p, geplante Aufgaben und /loop sind Thema in Kapitel 7. Parallele Sitzungen mit Worktrees in Kapitel 6.

14

Typische Stolperfallen

Diese Muster kosten am meisten Zeit. Zum Glück ist die Lösung jeweils einfach.

🍲 Die Allzweck-Sitzung

Problem: Du fängst mit einer Aufgabe an, fragst zwischendurch etwas ganz anderes und kehrst dann zurück. Der Kontext ist voll mit Fremdem.

Lösung: /clear zwischen Aufgaben, die nichts miteinander zu tun haben. Für kurze Zwischenfragen /btw.

🔁 Immer wieder korrigieren

Problem: Claude liegt daneben, du korrigierst, es liegt wieder daneben, du korrigierst wieder.

Lösung: Nach zwei erfolglosen Korrekturen /clear und ein neuer, besserer Prompt mit dem, was du gelernt hast.

📚 Die überladene CLAUDE.md

Problem: Die Datei ist so lang, dass wichtige Zeilen untergehen. Vieles darin könnte Claude ohnehin aus dem Code lesen.

Lösung: Nur aufschreiben, was Claude nicht selbst findet. Test: „Könnte es das im Code finden, und würde es nachsehen?“ Wenn ja, raus damit. Mehr in Kapitel 3.

🙏 Vertrauen ohne Prüfung

Problem: Claude sagt „fertig“, du übernimmst, und später fällt auf, dass ein Grenzfall fehlt.

Lösung: Immer eine Prüfung mitgeben und Belege verlangen. Wenn du es nicht prüfen kannst, liefere es nicht aus.

🕳️ Endloses Erkunden

Problem: „Untersuch mal“ ohne Grenzen. Claude liest Hunderte Dateien und füllt den Kontext.

Lösung: Untersuchung eng fassen („nur src/auth“) oder einem Subagenten geben, der nur eine Zusammenfassung zurückmeldet.

📣 Regeln mit Großbuchstaben

Problem: „WICHTIG: NIEMALS …“ in der CLAUDE.md, und es passiert trotzdem.

Lösung: Was nie passieren darf, gehört in eine deny-Regel oder einen Hook, nicht in lauteren Text.

Häufige Fragen

Muss ich auf Englisch prompten, damit es gut klappt?

Nein. Deutsch funktioniert genauso gut. Wichtig ist, dass der Prompt konkret ist, nicht die Sprache.

Wie lang sollte ein Prompt sein?

So lang wie nötig, so kurz wie möglich. Ein Satz mit Ort, Symptom und Ziel ist oft besser als ein Absatz voller Dinge, die Claude im Code ohnehin findet.

Sollte ich immer den Plan-Modus nutzen?

Nein. Er lohnt sich bei größeren oder unklaren Aufgaben. Bei kleinen, klaren Änderungen kostet er nur Zeit.

Bringt „denk ganz gründlich nach“ etwas?

Kaum. Das ist normaler Text. Wirklich mehr Denken bekommst du über /effort oder einmalig mit ultrathink im Prompt.

Verliere ich etwas mit /clear?

Nein. Das alte Gespräch bleibt gespeichert und ist über /resume erreichbar. Nur die neue Aufgabe startet ohne den alten Ballast.

Ist höherer Effort immer besser?

Nein. Er kostet mehr Zeit und Token. Bei alltäglichen Aufgaben ist das Ergebnis oft nicht besser als mit medium, bei max neigt Claude sogar zum Überdenken.
